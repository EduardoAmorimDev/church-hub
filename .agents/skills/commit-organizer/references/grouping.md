# Grouping a large change into commits

Load this from step 4 of `SKILL.md` when the change spans more than ~10 files,
or contains any rename, deletion or generated file.

**Contents:** What a "piece" is · The layer map · Signals that two files belong
together · Signals that they don't · Edge cases · Splitting a single file ·
Worked example: 23 files · When grouping fails

## What a "piece" is

A piece is a set of files that a reviewer would want to read at the same time,
and that a `git revert` could remove without leaving the tree broken. Those two
tests agree far more often than they disagree, and where they disagree the
revert test wins — a commit that cannot be reverted cleanly is the one that
hurts months later.

The wrong instinct is to group by *kind of file*: all the types in one commit,
all the tests in another, all the stories in a third. That produces commits
nobody can review, because no single one of them contains a whole thought, and
it breaks the revert test for every one of them.

## The layer map

This monorepo's layers, from lowest to highest. Commit order follows it
(step 5), and it is also the first cut for grouping, because a piece rarely
spans more than two adjacent layers:

| Layer | Paths |
|---|---|
| Dependencies | any `package.json` dependency block + root `package-lock.json` |
| Workspace & tooling config | `turbo.json`, root `package.json` scripts, `.prettierrc`, `packages/typescript-config`, `packages/eslint-config`, per-app `tsconfig.json` / `eslint.config.mjs` / `next.config.js` / `postcss.config.mjs` / `jest.config.mjs` |
| Design tokens | `packages/tokens/src` (`@church/tokens`) |
| Types & enums | `packages/ui/src/models/{enums,types}` |
| Helpers | `packages/ui/src/lib` (tailwind-variants, tailwind-merge), `packages/ui/src/components/utils` |
| Storybook config | `packages/ui/.storybook` |
| Design system | `packages/ui/src/components/{atoms,molecules,organisms}` |
| Routes & screens | `apps/web/app` (Next.js App Router), `apps/native/app` (expo-router) |
| Docs | `packages/docs`, `docs/`, `*.md` |

A new workspace under `apps/` or `packages/` (a planned backoffice, landing
page, or an extracted design-system package) slots in by what it is: a package
consumed by the apps sits with tokens, below the apps; a new app sits with the
routes. Its scaffolding (`package.json`, `tsconfig.json`, lint config) is one
piece; its first real feature is the next.

A change that touches a design-system atom and an `app/` route is two pieces,
not one, even when the route only changed because the atom did. The atom's
commit is the change; the route's commit is the adoption. The same holds across
workspaces: a token added in `packages/tokens` and first used in `apps/web` is
the token commit, then the consumer commit.

## Signals that two files belong together

- **Same component folder.** `Button.tsx`, `index.ts`, `Button.stories.tsx`,
  and any `Button.spec.tsx`, `Button.styles.ts`, `Button.types.ts`,
  `Button.context.ts`, plus the folder's `components/`, `data/` and `hooks/`
  subfolders — one piece, always. Folder membership decides, not the filename
  shape.
- **A test and its subject.** Non-negotiable (Principle I). If the spec was
  written in this run for code written in this run, they are one commit. Only
  `packages/ui` has Jest specs today.
- **A story and its component.** The story is the component's documentation;
  it ships with it.
- **A type and its only consumer.** One consumer means the type is not yet
  shared; splitting it produces a commit whose only content is an unused
  type.
- **A Storybook decorator and its only story.** Same logic: a decorator added to
  `packages/ui/.storybook` for one story is part of that story's piece.
- **A generated file and its generator input.** `apps/web/next-env.d.ts` and
  `apps/native/nativewind-env.d.ts` are tracked and regenerated by their tools;
  they belong with the change (typically a Next.js or nativewind bump) that
  made them change. Committed alone, they read as an unexplained churn diff.
- **A barrel and what it exports.** `index.ts` edits ride with the export they
  add or remove — including `packages/ui/src/models/{enums,types}/index.ts`.
- **A translation of one behaviour across sibling files.** If the same rule was
  applied to `TextField` and `TextArea` because it is one rule, that is one
  piece — the commit's subject is the rule, not the files.

## Signals that they don't

- **Different layers, with the lower one usable on its own.** Split.
- **Different workspaces, with the lower one usable on its own.** Split,
  lower workspace first.
- **One is a rename, the other an edit.** Split, always (see below).
- **One is formatting-only.** Split, always.
- **A dependency bump plus the code that uses the new version.** Split: bump
  first, adoption second. The bump is independently revertible and the adoption
  is not.
- **Two unrelated fixes that happen to sit in one folder.** Folder membership is
  a strong signal, not a rule. Two bugs are two commits.
- **"While I was in there" cleanups.** Their own ♻️ or 🎨 commit. They are the
  most common cause of a diff nobody can review.

## Edge cases

**Renames and moves.** Detect them through the index (`git add -A` then
`git diff --cached -M --name-status`) — an editor rename looks like an unrelated
delete plus an untracked file otherwise. Stage both the old and the new path in
the same `git add`, or git records a delete and an add instead of an `R`. A
rename commit is 🚚 and contains nothing else. When a rename comes with edits to
the moved file, that is two commits: the move, then the edit — in that order, so
the second diff shows only the edit.

**Deletions.** 🔥 when the removed code is still referenced or reachable
elsewhere (sunsetting a feature); ⚰️ when it is confirmed dead. Confirm before
choosing: grep for the symbol across `apps/` and `packages/` and say what the
grep returned. A deletion that also removes the last consumer of something else
leaves dead code behind — that is a second piece, not an oversight to fold in
silently.

**Formatting-only.** Verify it really is:

```bash
git diff -w --ignore-blank-lines --stat -- <file>     # empty = formatting only
```

Both flags are needed. `-w` alone ignores whitespace *within* a line but still
reports an added or removed blank line, so a Prettier run that reflows blank
lines survives `-w` and gets misclassified as a real change. Do not reach for
`-b -B` instead: `-B` is `--break-rewrites`, not "ignore blank lines". If the
diff survives both flags, it is not formatting and needs a real
classification. A reordered Tailwind class list is not whitespace — it survives
both flags and is a 💄 or 🎨 call for the convention to settle.

**Generated artifacts.** Beyond the two `*-env.d.ts` files: any file a script
produces. If the source change is in this run, they group. If the artifact
changed and no source in this run explains it, the artifact is stale or a side
effect of tooling — say so and ask rather than committing an unexplained
regeneration. The tokens CSS (`packages/tokens/dist/styles/root.css`) is
generated but gitignored; if it shows up, the ignore rules drifted.

**Lockfile without a manifest change.** `package-lock.json` moving alone usually
means someone ran `npm install` and it resolved a floating range differently.
Ask before committing it. If the user confirms it is intended, it gets its own
⬆️ commit, with a body saying it was a resolution refresh rather than an
intentional bump — otherwise the next reader assumes a deliberate upgrade.

**Files that only changed because of a mass edit** (an import path rewrite, a
renamed symbol). One commit for the mechanical sweep, named for the sweep
(♻️ or 🚚), separate from the change that made it necessary. Say the count in
the body: "updates the 6 call sites" is the useful fact.

**A spec that fails on purpose.** 🧪, its own commit, and only when deliberate
(TDD red step, reproducing a bug before fixing it). Never leave a failing spec
inside a ✅ or ✨ commit — the commit claims a passing state it does not have.

## Splitting a single file

The default is **don't**. A file is the atom, because a partially staged file
frequently does not compile, and step 5's ordering guarantee assumes every
commit type-checks.

Split one only when all three hold:

1. The file genuinely contains two unrelated changes (not one change you would
   like to describe in two sentences).
2. Each partial state type-checks on its own — verify it, do not assume it.
3. The user confirmed the split explicitly, for that file.

When splitting, stage hunks by path with an explicit patch rather than
interactive mode:

```bash
tmp="${TMPDIR:-/tmp}"                     # never a hardcoded path, never inside the repo
git diff -- <file> > "$tmp/piece.patch"   # edit the patch down to the hunks wanted
git apply --cached "$tmp/piece.patch"
git diff --cached -- <file>               # confirm exactly the intended hunks
```

Write the patch outside the working tree — a scratch file left inside the repo
becomes an untracked entry in the very inventory step 3 just took.

`git add -p` is interactive and cannot be driven reliably from a
non-interactive tool call; a hand-trimmed patch applied with `--cached` is
inspectable before it becomes a commit.

## Worked example: 23 files

A change that adds a `Popover` molecule to the web design system. The inventory
(through the index, so the rename resolved):

```
M  apps/web/package.json, package-lock.json      (adds @radix-ui/react-popover)
R  packages/ui/src/components/utils/getClonedIcons.ts -> …/utils/cloneIcons.ts
M  …6 files importing getClonedIcons
M  packages/tokens/src/colors.ts                 (adds overlay colours)
A  packages/ui/src/models/enums/PlacementEnum.ts
M  packages/ui/src/models/enums/index.ts
A  packages/ui/src/components/molecules/Popover/{Popover.tsx,Popover.styles.ts,
     Popover.types.ts,Popover.spec.tsx,Popover.stories.tsx,index.ts}
M  packages/ui/.storybook/decorators.tsx            (overlay root, used only by Popover story)
M  packages/ui/src/components/atoms/Tooltip/{Tooltip.tsx,Tooltip.spec.tsx}
M  apps/web/app/page.tsx                         (prettier only)
A  .env.development
```

Seven commits, in order:

| # | Commit | Files | Why this cut |
|---|---|---|---|
| 1 | `➕ chore(web/package): adds @radix-ui/react-popover` | 2 | Dependency alone, first, with the lockfile |
| 2 | `🚚 refactor(web/utils/clone-icons): renames getClonedIcons` | 7 | The move plus its 6 call sites; nothing else. Body states the count |
| 3 | `✨ feat(tokens/colors): adds overlay colour tokens` | 1 | Lower workspace before the app that consumes it |
| 4 | `🏷️ feat(web/models/enums/placement-enum): adds PlacementEnum` | 2 | Two consumers downstream (Popover, Tooltip), so it earns its own commit; barrel rides along |
| 5 | `✨ feat(ui/molecules/popover): adds Popover` | 7 | Folder + spec + story + the decorator only its story uses |
| 6 | `♻️ refactor(ui/atoms/tooltip): places Tooltip via PlacementEnum` | 2 | Independent adoption of the enum, own spec |
| 7 | `🎨 style(web/app/page): applies prettier formatting` | 1 | Whitespace only, verified with `git diff -w --ignore-blank-lines` |

`.env.development` is quarantined — it is not gitignored here. 23 files
inventoried, 22 committed, 1 reported as left behind.

Decisions worth noticing. The rename (2) lands before the Popover (5) because
the new component imports `cloneIcons` by its new name; with the order reversed,
commit 5 would not type-check. The decorator went with the Popover rather than
into a Storybook-config commit, because it exists only for that story — alone
it would be unused config. And the emoji of 4 is the types value, not the
feature value, even though the branch is a feature: the commit's own diff is
only an enum. Emoji choices here are illustrative — the priority order in
`<repo>/docs/commit-convention.md` decides them in a real run.

## When grouping fails

If, after applying everything above, the change still refuses to cut into
coherent pieces, that is information about the change, not about the method.
Two common causes and what to do:

- **One genuinely atomic change touching many files** — a rename sweep, a
  framework upgrade (Next.js, Expo, Tailwind), a repo-wide codemod. One commit
  is correct here. Say why in the body and give the count.
- **Two features implemented at once, interleaved in the same files.** They
  cannot be separated without splitting files, and splitting files breaks the
  build. Say so plainly, propose one commit per file-set with a body naming
  both features, and note that this is a consequence of how the work was done
  rather than something the commits can fix.

In both cases, report the reason rather than producing an arbitrary split. An
arbitrary split is worse than one honest large commit: it looks reviewed.
